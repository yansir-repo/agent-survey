# 目标：把一次客户访谈的记录，变成开发者拍板的一组建站决定

## 这场是谁

这场访谈的对象是**我们自己的开发者**（下面协议里说的“受访者”，在这场都指他）。他是专家，时间比客户更贵：能选的不要让他写，能一次问完的不要拆两轮。

协议里“受访者不是专家”“不要问看不懂的技术问题”“怎么实现是我方的活，不要问他”——**这场不适用**：开发者就是实现方，页面结构、内容模型、字段、路由、表单去向正是这场要问的。不要问的是：视觉细节（颜色、间距、字体）、代码怎么写、报价和工期承诺。

## 已知信息（先读）

工作区的 `provided/` 下是这场访谈开始前放进来的资料：

- `provided/respondent/`（受访者提供的）：这里放的是**客户访谈的原始问答**，是你判断“客户到底要什么”的唯一事实来源。
- `provided/inquirer/`（提问方的整理）：对客户访谈的整理和说明。**这是我们的判断，不是客户的话**；和客户原话冲突时以原话为准，并把冲突记下来。

先读完，再发第一轮。

## 你要问出来的

1. **先起草，再问。** 在 `/NOTES.md` 里写下你的草案：页面清单（每页一句话职责、形态是单页 / 列表 / 详情模板 / 工具页 / 表单页）、内容模型（有哪些东西、靠哪些属性比较、怎么分组、哪些多语言要翻）、范围外、待确认、风险。草案要具体到开发者能直接说“行 / 改成这样”。
2. **只问不可逆的决定。** 页面增删和取舍、内容类型和路由、字段与多语言口径、表单收到的东西去哪、媒体边界、第一期不做什么。能靠默认值解决、以后改起来便宜的，自己定，并作为你的解读记下来（`note_finding`），不要问。
3. **每个问题是一个决定，不是一道题。** 3–6 题一轮；优先单选 / 多选；每题给 2–3 个选项、你的推荐、每个选项的代价（多一个模板、多一轮翻译、多一个要维护的地方）。只有“为什么”才用 text。
4. **不问客户已经答过的事实。** 客户原话里有答案的，直接用；拿不准的，用 confirm 复述客户原话让开发者确认，不要重新问一遍。
5. **开发者说“你定”** → 给默认方案，作为解读记下来并标明“我方决定”，继续；不要追着要他拍板。

## 完成的判据

下面都成立，才结束（验收时只看这场访谈的原始问答）：

1. 页面的增删和取舍有开发者的回答（或他明确说“你定”）。
2. 内容类型和路由有开发者的回答。
3. 字段与多语言口径有开发者的回答。
4. 表单的去向（存不存、通知谁、之后发生什么）有开发者的回答。
5. 媒体的边界（图片 / 视频 / 文件怎么进、谁维护）有开发者的回答。
6. “第一期不做什么”至少有一条。

## 不要做

- 不写代码、不定视觉、不报价、不承诺工期。
- 不替开发者做决定；他不表态的，给默认方案并标明“我方决定”。
- 不编客户没说过的事实；原话和整理冲突时以原话为准，并记下冲突。
- 不用占位邮箱 / 占位域名 / 假电话：不知道就写“待确认”。
- 不把这场的内容发给客户；这是内部访谈。
